rsrc_windows_amd64.syso in this directory embeds three things into
streaming-tree-server.exe itself: the application icon, its version-info
metadata (ProductName/FileDescription = "Streaming Tree for OBS", so
Explorer's Properties dialog identifies it correctly), and - since the
Stage 20E DPI remediation below - a real application manifest declaring
Per-Monitor-V2 DPI awareness.

Go's toolchain links any *.syso file present in a main package's own
directory automatically - no build flag, no change to build-release.ps1
or any workflow needed. The _windows_amd64 suffix restricts it to
windows/amd64 builds only, via the exact same filename-based build-
constraint mechanism *_windows.go source files already use throughout
this codebase - a Linux/macOS/cross-compiled build simply never sees
this file (re-verified after every regeneration below).

This is a generated, checked-in derivative, produced by the go-winres
tool (https://github.com/tc-hib/go-winres, pure Go, no gcc/windres
needed) from winres/winres.json in this directory - not regenerated by
any build script. Regenerate it by hand only when the icon, version
metadata, or manifest settings need to change:

    go install github.com/tc-hib/go-winres@latest
    go-winres make --arch amd64 --in apps/server/cmd/server/winres/winres.json \
      --out apps/server/cmd/server/rsrc

winres.json's own "RT_GROUP_ICON" entry points directly at this
project's one canonical icon (internal/runtime/tray/assets/tray.ico,
itself generated from assets/branding/streaming-tree-logo.png by
scripts/generate-branding-assets.go - see that script's own doc comment
for the full source-of-truth chain) - never a second copy of the
artwork. IMPORTANT: that entry must be a bare JSON string
("tray.ico"), never a single-element array (["tray.ico"]) - go-winres's
own array-of-icon-files code path always treats every array element as
a plain raster image via the standard image.Decode, which cannot parse
a multi-frame .ico container and fails with "image: unknown format";
only the bare-string form takes the dedicated winres.LoadICO fast path.
Found and fixed by direct source reading of github.com/tc-hib/go-winres
during this remediation, not by guessing.

Every string field under "RT_VERSION"."#1"."0000"."info"."0409" must be
non-empty for Windows' own version-info APIs (and anything built on
them, including .NET's FileVersionInfo/PowerShell's
(Get-Item file).VersionInfo, which Explorer's Properties dialog
ultimately also reads through) to parse the resource at all - leaving
FileVersion/ProductVersion blank while filling only
ProductName/FileDescription produced a StringFileInfo block that looked
fine under a raw byte-level resource dump but which those APIs silently
failed to read (every field, including the ones that were filled in,
came back empty). Found by directly comparing raw RT_VERSION resource
bytes (present and correct) against .NET's own parsed result (empty)
after the same regeneration - a real, verified defect in the resource
structure, not assumed. Fixed by giving every field in that block a
real value. FileVersion/ProductVersion ("0.1.0.0") are still a static
placeholder, not the real per-build version
(buildinfo.EffectiveVersion(), injected via -ldflags at release-build
time): Windows' VERSIONINFO resource's numeric/string version fields
don't represent this project's real version strings (which carry a
manual/test suffix like "0.1.0-manualtest+<commit>" outside a real
release - see docs/updater.md §43) well, and keeping this resource a
checked-in, hand-regenerated file (like every other generated asset in
this pipeline) deliberately avoids adding go-winres as a per-build CI
dependency just to keep these strings in sync.

## DPI awareness (Stage 20E branding-remediation follow-up)

A real physical/manual Windows retest found the tray's native popup
menu text visibly blurry compared to another normal Windows tray
application at the same display scale. Audited (not assumed): the
previously-shipped rsrc_windows_amd64.syso was built with
`--manifest none` (a deliberate scope-minimization choice at the time -
see the git history of this file), so the executable carried no
application manifest at all and therefore ran under Windows' default
DPI_AWARENESS_CONTEXT_UNAWARE - confirmed by extracting the real
RT_MANIFEST resource (id 1, type 24) from the actual built .exe via
FindResource/LoadResource/LockResource and finding none present, not by
reading source alone.

Fixed via winres.json's "dpi-awareness": "per monitor v2" field, which
go-winres compiles into the standard Microsoft-documented fallback
manifest:

    <dpiAware ...>true</dpiAware>
    <dpiAwareness ...>permonitorv2,system</dpiAwareness>

(PerMonitorV2 on Windows 10 1703+; falls back to system-DPI-aware, never
all the way to unaware, on older Windows). Per Microsoft's own
documentation (learn.microsoft.com/windows/win32/hidpi/dpi-awareness-
context): "All NTUSER menus created in Per Monitor v2 contexts will be
scaling in a per-monitor fashion" - a manifest-level, process-wide
declaration is sufficient; no separate menu-specific API call or
per-thread DPI context is needed, and none is used here.

Verified, not just embedded: after rebuilding, the real RT_MANIFEST
resource was re-extracted from the built .exe and confirmed to contain
exactly the XML above. Then the real packaged executable was run (a
real `buildinfo.Packaged()` build via build-release.ps1, not a plain
`go build` - the tray only initializes in a packaged build) and its own
hidden tray window's live DPI context was queried directly via
GetWindowDpiAwarenessContext + AreDpiAwarenessContextsEqual against
DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2 - confirmed true (and
confirmed NOT equal to the v1 context, ruling out a "per monitor but
only v1" false positive) - on this development machine's own real
display, which GetDpiForWindow on that same window reported as 120 DPI
(125% scale), not the 96 DPI (100%) an earlier, DPI-unaware measurement
tool on this same machine had reported for "the system DPI" - itself a
live demonstration of the exact DPI-virtualization mechanism this fix
addresses: an unaware caller gets a virtualized, not a real, DPI
answer. This proves the manifest is honored and the tray's own window
is correctly Per-Monitor-V2-aware before any DPI-sensitive object
(including the popup menu) is created. The remaining, necessarily
manual step - whether the menu now looks visually crisp - is the real
physical/manual Windows retest this fix is built for; automated
tooling cannot judge that.
