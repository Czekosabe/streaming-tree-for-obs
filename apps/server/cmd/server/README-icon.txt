rsrc_windows_amd64.syso in this directory embeds the application icon
(and a minimal Windows resource - see below) into streaming-tree-server.exe
itself, so Explorer, Alt-Tab, and the executable's own Properties dialog
show the real Streaming Tree for OBS icon rather than Go's generic default.

Go's toolchain links any *.syso file present in a main package's own
directory automatically - no build flag, no change to build-release.ps1
or any workflow needed. The _windows_amd64 suffix restricts it to
windows/amd64 builds only, via the exact same filename-based build-
constraint mechanism *_windows.go source files already use throughout
this codebase - a Linux/macOS/cross-compiled build simply never sees
this file.

This is a generated, checked-in derivative, produced by the go-winres
tool (https://github.com/tc-hib/go-winres, pure Go, no gcc/windres
needed) pointed at this project's own single canonical icon
(internal/runtime/tray/assets/tray.ico, itself generated from
assets/branding/streaming-tree-logo.png by
scripts/generate-branding-assets.go - see that script's own doc comment
for the full source-of-truth chain). It is not regenerated by any
build script; regenerate it by hand only when the icon changes:

    go install github.com/tc-hib/go-winres@latest
    go-winres simply --arch amd64 --manifest none \
      --icon apps/server/internal/runtime/tray/assets/tray.ico \
      --product-name "Streaming Tree for OBS" \
      --file-description "Streaming Tree for OBS" \
      --product-version "0.1.0.0" \
      --file-version "0.1.0.0" \
      --original-filename "streaming-tree-server.exe" \
      --out apps/server/cmd/server/rsrc

--product-version/--file-version are a static placeholder, not the
real per-build version (buildinfo.EffectiveVersion(), injected via
-ldflags at release-build time): Windows' VERSIONINFO resource's
numeric fields are strictly 4-part major.minor.build.revision and
cannot represent this project's real version strings (which carry a
manual/test suffix like "0.1.0-manualtest+<commit>" outside a real
release - see docs/updater.md §43), and keeping this resource a
checked-in, hand-regenerated file (like every other generated asset in
this pipeline) deliberately avoids adding go-winres as a per-build CI
dependency just to keep four numbers in sync. The value here is
intentionally the hand-maintained internal/buildinfo.Version base
(currently "0.1.0"), not dynamically wired to any real build.

--manifest none is deliberate: this remediation is scoped to branding
(icon/tooltip identity) only. A Windows application manifest also
controls DPI awareness, UAC execution level, and Common Controls
version - none of that has been reviewed or requested here, and adding
one as a side effect of an icon fix would be exactly the kind of
scope creep this project avoids. If a real manifest is ever wanted, it
should be its own deliberate, reviewed change.
